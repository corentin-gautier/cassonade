# Contributing to Cassonade

Thanks for wanting to help. This file covers everything that is not about playing: building and testing the mod, how each feature works under the hood, the texture pipeline, translations, commits and releases. What the mod does for players is in the [README](README.md), which is also the reference for the expected behavior.

## The spirit of the mod

Before adding anything, check it fits:

- No new ores, gear tiers, magic, machines, mobs, biomes or dimensions. Nothing that makes the game easier to beat, only nicer to play.
- A new feature is unlocked by equipping a vanilla item (compass, clock) or one crafted from vanilla items (backpack, world map). Vanilla progression does not change.
- The interface keeps Minecraft's pixel style and sounds, in the mod's art direction (sepia wood, dark slots, leather, cream paper).
- On a server without the mod, the client must stay usable: features that need the server fall back to vanilla behavior.

## Getting started

The project needs Java 25. Gradle downloads it automatically for this project (see `gradle/gradle-daemon-jvm.properties`): there is nothing to install.

- `./gradlew runClient`: launches the game with the mod (username `Corentin`, offline, worlds in `run/`).
- `./gradlew build`: builds the jar in `build/libs/`.
- `./gradlew runClientGameTest`: the end-to-end test in the real client (see [Tests](#tests)).

Without a terminal, there are two other ways to launch the game with the mod:

- **From VS Code**: `Cmd+Shift+B`. The other actions (automated tests, building the jar) are under `Cmd+Shift+P` → "Tasks: Run Task".

The game opens offline: no Microsoft account needed, but online multiplayer is not available. Test worlds are saved in `run/` and come back at each launch. The first launch takes a few minutes (downloading Java 25 and Minecraft), the next ones about 30 seconds.

In `runClient` only (never in a player's game), commands save crafting and travelling to try a feature, in a world with cheats on ([DevCommands](src/main/java/com/cassonade/dev/DevCommands.java)):

- `/dev kit` fills every gear slot with its best item (sculk compass, world map, barometer, elytra, organized backpack) and gives the rest: both spyglasses, the sculk torch, the diving mask, fireworks, two waystones, a woodcutter, hoppers, a plain backpack and the upgrade template. What was worn goes back to the inventory.
- `/dev unequip` empties the gear slots into the inventory, to see the game without them.
- `/dev goto biome <biome>` and `/dev goto structure <structure>` find the nearest, as `/locate` does (tags too: `#minecraft:village`), and stand you on a floor there: on the surface, in the cave for a cave biome (`lush_caves`, `deep_dark`), on solid ground, in the heart of a structure, buried or not (`ancient_city`, `stronghold`). Only in the current dimension: `/execute in minecraft:the_nether run dev goto …` for another.
- `/dev goto town` stands you at the nearest town's meeting point (a rare, larger village).
- `/dev goto tavern` stands you in the nearest village's tavern, rare enough that looking for one by hand takes long: it goes over the villages' grid ring by ring, up to 24 regions away, making only each spot's structure starts to read its houses.
- `/dev regen` makes the terrain again from scratch, to see a change to world generation in a world already played: the command leaves a mark in the save, and the next time the world opens, before any chunk loads, every dimension's `region`, `entities` and `poi` folders are deleted, with the world map's exploration ([ChunkReset](src/main/java/com/cassonade/dev/ChunkReset.java)). So: `/dev regen`, quit, change the code, relaunch, reopen the world. Players, their inventories and the mod's saved data (markers, waystones) stay; each player is stood on the new ground as they join.
- `/ambience <effect>` calls an ambience effect at once (see [AmbienceCommands](#how-the-features-work)).
- Keys run them, rebindable in the controls with the mod's keys ([DevKeys](src/client/java/com/cassonade/client/dev/DevKeys.java)): `F6` `/dev kit`, `F7` `/dev unequip`, `F8` `/dev regen`, which a second press takes back, and `F9` and `F10` open the chat on `/ambience ` and `/dev goto `, ready for the argument and its suggestions (`fn` with them on a Mac).
- Vanilla covers the rest: `/loot give @s loot minecraft:chests/jungle_temple` rolls a chest's loot, `/place structure` builds a structure where you stand, `/time set night`, `/weather rain`.

`-Ptests=DevCommands` checks them.

## Project layout

- `src/main`: shared by client and server (items, slots, recipes, network payloads, server mixins). One package per feature (`gear`, `compass`, `hopper`, `combat`…), each registered by an `init()` called from `Cassonade`.
- `src/client`: rendering and screens (HUD, minimap, map, journal), entry point `CassonadeClient`.
- `src/gametest`: automated client tests.
- Mixins are declared in `cassonade.mixins.json` (main) and `cassonade.client.mixins.json` (client).
- `src/main/resources/data/minecraft/recipe`: rebalanced recipes, generated by `tools/rebalance_recipes.py`, never edited by hand.
- `tools/`: Python scripts, without dependencies, that draw the textures and generate the recipes.

Code style: tabs for indentation, comments in English that explain the why, at the density of the surrounding code. Follow the style of the file you are editing rather than introducing new patterns.

## Tests

Advancement banners and recipe toasts are off in the tests, by mixins of their own (`src/gametest/.../mixin`): they cost time and cover screenshots. A test about them sets `TestNotifications.shown`.

`./gradlew runClientGameTest` launches the game in automated test mode (`src/gametest`). It creates a world, equips the backpack, the compass and the world map, explores and opens the world map, places a named marker then removes it, changes the marker display, opens and closes the backpack with `B`, checks hand refill, bulk crafting and map previews, takes pictures of the restyled windows, sets a hopper's filter, checks saving and death, then closes the game. Other test classes join a dedicated server with the mod and Minecraft's own server without it.

- `-Ptests=Gear,Quest` runs only those tests (the class name without `ClientGameTest`: `Gear`, `WorldMap`, `Storage`, `Hopper`, `Everyday`, `Screens`, `Murmuration`, `NightSky`, `AirSounds`, `AmbientSound`, `Insects`, `Motes`, `ShootingStars`, `HeatLightning`, `JumpingFish`, `Breath`, `Waves`, `Foam`, `AmbienceCommands`, `DevCommands`, `JungleTemple`, `PirateBooty`, `VillageStone`, `Town`, `Tavern`, `Birds`, `DarkBirds`, `Mist`, `Quest`, `QuestOffer`, `Interface`, `Clock`, `Tweaks`, `ArmorStand`, `Lights`, `Anvil`, `Bookshelf`, `Cauldron`, `SnowShovel`, `EnderChest`, `Woodcutter`, `Loom`, `FlowerPot`, `VehicleExit`, `SignEdit`, `BookEdit`, `FacingPreview`, `OrganizedBackpack`, `Combat`, `Markers`, `MarkerLabels`, `StrayMobs`, `Inventory`, `Search`, `Tooltips`, `Workstations`, `InfoPanels`, `WorldSelection`, `Spyglass`, `Glance`, `HiddenEntities`, `MinimapFollow`, `CaveMinimap`, `HideMinimap`, `SoundPlaces`, `GearComparison`, `RecipeUses`, `WorldMapTextures`, `DedicatedServer`, `VanillaServer`). `-Ptests=InfoPanels` opens every GUI that uses an info icon and saves a screenshot for each. Run the tests your change touches; while working on a feature, a small test of its own (like `Clock`) runs much faster; give a new feature its own test rather than growing an existing one.
- Screenshots, in 1920×1080, are in `build/run/clientGameTest/screenshots/`.
- `-Pprofile` measures frame rates on the world of `-PexploredWorld`, kept in `.test-worlds/explored-world` like the shots' world, out of reach of `clean` (`ProfileClientGameTest`): the medians in the log, a Flight Recorder file per situation in `build/profile`, read with `python3 tools/profile_report.py <JDK>/bin/jfr`. The same scene varies a lot between runs: compare situations within a run, not across runs. `-Pprofile -Ptests=PlayerProfile` (`PlayerProfileClientGameTest`) is the short one, about a minute: a new world, everything of the mod worn, running over chunks being made, with each slow frame's moment in the log.
- `-PsiteScreenshots -Ptests=SiteWorldUpgrade` brings the shots' world up to the villages as they are generated now (`SiteWorldUpgradeClientGameTest`): each village piece is compared with its vanilla template read from the game's jar, and only blocks still the template's are upgraded (churches to taverns, cobblestone to stone bricks), what was placed by hand stays. It overwrites `.test-worlds/site-world`: copy the folder first.
- `-PsiteScreenshots -PsiteShots=ambience-night,ambience-mist` retakes only those shots (any shot's id), in under a minute. `-PsiteScreenshots` alone retakes the website's screenshots as PNG (the world they are taken in was prepared by hand in the game, with its scene, gear, waystones and explored map, and is kept in `.test-worlds/site-world`: a run works on a copy of it, and it cannot be made again, as nothing outside this folder holds it), which [tools/convert-screenshots.sh](tools/convert-screenshots.sh) turns into the site's AVIF and the stores' JPG (the VS Code task "Prendre les captures d'écran" runs both; see [promo/site/assets/screenshots/README.md](promo/site/assets/screenshots/README.md)).
- `-PsiteIcons` redraws the website's recipe icons of the blocks among the ingredients (`SiteIconsClientGameTest`, see [Documentation](#documentation)), apart from the screenshots.

Run them after any change to behavior or interface.

## Code quality audit plan

Review the codebase in bounded passes so each finding can be checked against the code and its tests:

1. **Map the codebase:** list source sets, feature packages, entry points, shared helpers, mixins, generated files and existing tests.
2. **Review shared foundations:** inspect registration and lifecycle, networking and persistence, common utilities, and server-side mixins for correctness, coupling and error handling.
3. **Review feature families:** inspect client features and screens in small groups, checking ownership, state lifetime, duplicated logic, complexity and whether behavior is covered by game tests.
4. **Review tooling and tests:** assess build configuration, texture/recipe generators and test coverage; verify generated files are not treated as hand-maintained sources.
5. **Validate and report:** run focused tests for confirmed issues, then the build; report only reproducible, actionable findings with severity, file/line references, suggested fixes and explicit coverage limits.

Keep the audit read-only until findings are prioritized. Fix confirmed issues in separate, focused changes, adding regression tests where practical; track unreviewed areas between passes so the final report distinguishes full coverage from sampling.

## How the features work

### Equipment slots

Instruments that show something on screen sit in the column above the offhand: compass, world map, clock. What is worn on the body follows the offhand along the bottom row: elytra, then backpack. Equipment is stored in a player attachment (`PlayerGear`). An item crafted from a slot's vanilla item goes in the same slot and unlocks more: the barometer (clock and lightning rod) in the clock's, the sculk compass (compass and sculk sensor) in the compass's. Their textures, and the website's copies in `promo/site/assets/items`, are generated from the game's textures by `tools/gear_item_textures.py`, as are the naturalist's spyglass's (spyglass, book and sculk sensor), which is held, not worn.

- Shift-click equips these items. With the backpack open, other items go into it (armor and shields keep their vanilla priority); closed, Shift-click stays vanilla. Picked-up items always go to the inventory.
- The inventory tabs open the recipe book (in place of the vanilla button), the backpack and, with a world map equipped, the world map. The open book also closes with its bookmark ribbon, the backpack with the strap of its flap.
- The backpack's contents live in the item (`DataComponents.CONTAINER`), like a Shulker box.
- The organized backpack (`gear/OrganizedBackpack`) is a `BackpackItem` of its own, made by a `smithing_transform` that copies the contents. Its template is added to chests through `LootTableEvents.MODIFY`. `HandRefill` falls back on it, `InventoryMixin` counts it for the recipe book on both sides, `ServerPlaceRecipeMixin` takes ingredients from it, `ItemEntityMixin` tops up its partial stacks on pickup.
- In Creative mode, the slots are not shown. On a server without the mod, which has nowhere to keep them, the slots, the backpack and the sort buttons are not offered.

### Loading screen

`WorldLoading` draws a world's first load, in singleplayer or joining a server, on the map of what was explored: in sepia (`RegionOverviews`), each loaded chunk coming into color; land never seen is hatched, then inked. In singleplayer the chunks come from the server's own view and the center from `LevelLoadTracker.updateFocus`; a server tells nothing, so the bar counts the chunks arrived around the player. The steps before (`GenericMessageScreen` by its translation key, `ConnectScreen`) use the same layout with blank paper, as does the one frame of `ProgressScreen` the game shows between them (`WorldLoading.between`). A portal or any later change of dimension has no chunk view and follows no connection, so it stays vanilla. Saving on leaving (`menu.savingLevel`) shows the world's name over a floppy disk, drawn by `tools/loading_textures.py`: the game tells nothing of its progress. `-PexploredWorld` takes the screenshots.

### Compass and world map

- Minimap zoom, rotation, hiding and marker display are kept in `config/cassonade.properties`.
- The world map item is the only one the map slot accepts. Its texture, a filled map in a frame of sticks, is generated from the game's textures by `tools/world_map_texture.py`.
- The minimap (`Minimap.tick`) moves its picture with the player and reads only the rows and columns coming into it, plus a few rows each tick so that the whole picture is read again in 2 seconds, for the blocks changed; it uploads the texture only when something changed. It reads in full on a change of zoom, world or Nether height, and while chunks are missing. Deep in an Overworld cave (`Minimap.underground`: no sky light and 8 blocks or more under the surface; it leaves above 3 of sky light or within 4 blocks of the surface, so it does not flicker at a cave's mouth), it reads a cut (`TerrainColors.Cut`) from the player's feet up to 4 blocks over the head, or up to the cave's ceiling when higher (16 at most, read in steps of 4): a column open somewhere in it shows the floor under its highest open block, one solid all through is a wall, drawn in one dark color rather than the rock's own (diorite and granite showed as blobs); it reads in full when the cut changes. Under the Nether's roof, the cut is the head's height alone. Both are read from the height the player took off from during a jump (`Minimap.groundY`), so that jumping reads nothing again; landing elsewhere, falling, swimming, climbing, flying or riding move it at once. `-Ptests=MinimapFollow,CaveMinimap`.
- Exploration is recorded at all times, even without a world map: chunks within 6 chunks of the player count as explored. They are read again when the player enters a chunk, when the world map opens or while chunks are missing, not continuously: that reading was the mod's largest cost on the render thread, and the map only serves to find one's way. Blocks changed just before a teleport, a death or leaving the world show on the next visit. The data stays on the client, in the world folder in singleplayer (`cassonade/worldmap`), in `cassonade/worldmap/servers/<address>` in the game folder in multiplayer.
- From 1/4 zoom out, the world map draws each region as a 128 × 128 overview (`RegionOverviews`), read on a background thread and kept for the session, redone from the loaded region when its colors change, a few textures made per frame: a whole explored world can then show without loading its regions in full. Regions are evicted from their cache between frames only, never while the map is open, since a texture released after being queued for drawing would have its id reused by another.
- Each region also saves the surface biome in 4 × 4 block cells, so holding `Shift` while hovering an explored area names its biome even after its chunk unloads (`TerrainColors`, `MapRegion`).
- The `Shift` tooltip adds the matching position in the other dimension, eight blocks to one, once the Nether has been explored (`WorldMap.visited`, in memory or on disk): the exploration data is the only record of a visit the client has.
- Markers are saved on the player (64 at most, across all dimensions) and kept on death. They are drawn as the vanilla map banners, each texture pixel a whole number of screen pixels so they stay sharp at any size (`MapDecorations.banner`). In the world, the banner and its label (in whole screen pixels per font pixel) shrink from 16 to 256 blocks away. Holding `MARKERS_IN_WORLD` overrides the display with the in-world one. `MarkersInWorld` hands the markers and waystones to `DirectionBar` by default, drawing in the world only those within 32 blocks along the ground, which the bar then does not name; pings and the death marker always go in the world. `LabelSpots` keeps labels apart, in the world (nearest first), on the minimap and on the world map: one moves up to three lines off, or is left out.
- The death marker is the game's own last death location, which it sends the client for the recovery compass: nothing from the server, it works anywhere. Once the player has gone more than 12 blocks away, coming back within 4 puts it away; that choice is kept next to the explored map (`dismissed_death.json`). Its icon is the treasure map's red X.
- The spawn chunk is the chunk of the world's spawn point, which the game sends every client: outlined in the paper color over a dark line, never under 6 GUI pixels wide, named on hover. Client only.
- Lodestones come from the `lodestone_tracker` of every compass carried (inventory, offhand, the compass's gear slot), in the current dimension, one marker per lodestone (`LodestoneMarkers`). Their icon is the vanilla map's white X (`target_x`). Client only.
- Coordinates in chat messages (three whole numbers, perhaps labelled x, y, z, a height of four digits at most) become links while the world map is worn and the server has the mod (`ChatCoordinates`). The link is a custom click event that `ScreenMixin` keeps on the client, opening the world map there with its name box.
- Minecraft saves keys by their position on a QWERTY keyboard; `M`, `B`, `N`, `+` and `-` follow the character printed on the player's keyboard instead. If the matching key is already taken, the zoom picks another: on a Mac AZERTY keyboard `+` is the command key, so zooming in moves to `)`; on a PC AZERTY keyboard `-` is hotbar slot 6, so zooming out moves to the numpad `-`.

### Clock

The forecast comes from the server every second to the players wearing a barometer, read from its weather timers. It is not shown on a server without the mod, nor when the weather is frozen (`advance_weather` set to `false`). When a thunderstorm could start or stop before the next rain change, the game rolls for it later: the forecast then simply says rain. The weather icons, the moon's phases and the bed are in the interface atlas, drawn by `tools/gui_textures.py`. The moon's phase is the game's own (the `visual/moon_phase` environment attribute), shown where there is weather, so in the overworld. When a bed would let the player sleep, the chime rings and the moon blinks with the bed for 5 seconds, half a second each, in the moon's place so the panel keeps its width, on the client: at nightfall or as a thunderstorm starts, not when joining at night.

### Storage

- Sorting merges identical stacks then orders them by item. It touches the 27 inventory slots, never the hotbar or armor; stashing does not take from the hotbar either, and needs the chest open.
- Shift-drag moves each hovered stack as if it were Shift-clicked, until Shift or the button is released. In the Creative inventory, Shift-click keeps its usual behavior.
- Scrolling down over a stack takes it, puts one item back, Shift-clicks that item, then puts the rest back: vanilla clicks only, so it works on any server, and the item lands where the menu's own Shift-click sends it. Scrolling up does nothing, and a bundle keeps the wheel for choosing its item. Not in the Creative inventory, nor on a locked slot. Trackpad scrolling adds up to a full notch per item.
- Locked slots are kept on the player by the server (one bit per inventory slot, hotbar included), kept on death and synced to its own client. The server skips them when sorting and stashing, and a Shift-click does not fill them when empty (it still tops up their stack); the client does not send a Shift-click from them, nor the drop key, in a window or on the selected hotbar slot (`MultiPlayerGameModeMixin`). Hand refill ignores them, to keep refilling a locked hotbar slot. A left click with the lock key held (`Alt` by default) toggles a slot; screens do not update key mappings, so the client checks the bound key itself. It works in every container window but the Creative inventory, and not on a server without the mod. The padlock is in the interface atlas.
- Inventory sounds are the bundle sounds, at different pitches depending on the gesture.
- Container previews show nine slots per row, three rows at most with the count of the other items in the last slot, and an amber fill bar. Tooltips have 6 pixels of inner padding instead of 3. An unopened loot Shulker box keeps the game's "???".
- The server only sends a map's contents when it is in the player's inventory: a map never carried keeps the vanilla tooltip.
- With food in hand that the player could eat (main hand first, as the use key), the drumsticks it would restore blink on the hunger bar, the game's own sprites faded in and out (`HudFoodPreviewMixin`). Client only.
- Tooltips' secondary text (enchantment descriptions, fuel, anvil penalty, food and map labels, a container's state, the hopper filter's line, the world map's coordinates and hints) has one size, a GUI scale step smaller (`SmallText`), and one color (`DescriptionText.COLOR`). Lines of text carry an invisible mark (`DescriptionText.of`) that `ClientTextTooltipMixin` recognizes; the game's own gray lines stay as they are. Enchantment names are in the interface's cream (`DescriptionText.NAME_COLOR`), curses in red. Attributes follow the same hierarchy (`ItemStackAttributesMixin`): "When in Main Hand:" as secondary text, a heading (`DescriptionText.HEADING`: room above instead of vanilla's blank line, and 3 pixels under it), the values in cream; the gear comparison colors only its difference, green or red by the game's own verdict on the attribute; the creative tabs under an item's name are secondary text too (`CreativeModeInventoryScreenMixin`).
- Food tooltips draw two named lines of the hunger bar's own drumstick sprites, two points to a drumstick: the hunger restored, then the saturation, the same sprites tinted gold, its points rounded up. Client only.
- Enchantment descriptions are in the language files, `gui.cassonade.enchantment.<namespace>.<path>`; an enchantment without one (from a data pack or another mod) shows its name alone. They are wrapped at 180 pixels. Client only: it works on any server.
- The anvil penalty is the item's own `repair_cost`, which the game adds to every anvil use and doubles, plus one, each time. Shown from 1 level, as the tooltip's last line. Client only.
- An anvil rename with no repair or enchantment operation costs no levels (`AnvilMenuMixin`); repair and enchantment operations keep their vanilla cost.
- Fuel burn times are data-driven providers in a loot context only the server can build: it reads them as a furnace would and sends them on joining and after a data pack reload (`furnace/FuelTimes`). A blast furnace or smoker burns twice as fast and cooks twice as fast, so a furnace's 200 ticks per item gives the count for all three. The line shows only in their windows; on a server without the mod, not at all.
- A brewing stand's own menu syncs the remaining brew time and fuelled batches to every client. `BrewingStandScreenMixin` shows those values without a server payload; the active batch is included in the remaining count.
- Storage search is client-only. `ContainerSearch` opens a field above the window, framed like a small window (`tools/search_field_texture.py` cuts it from the inventory's edge), from the small `F` button or Ctrl/Cmd+F, and dims non-matching storage slots without hiding them. It searches names, item IDs, enchantment names and IDs, and nested bundle or Shulker box contents.
- The list of items picked up comes from the packet the server sends every client when a player picks something up, vanilla or not, read before the game takes the amount off the item on the ground. Arrows and tridents are left out (they are not item entities). Client only.
- Hand refill prefers an identical stack (same enchantments, same wear) and only searches the inventory, then an organized backpack, never the plain one. Dropping or moving a stack does not trigger it.
- Bulk crafting leaves what does not fit in a full inventory in the grid.
- **An item's uses** (`RecipeUses`, `RecipeBookComponentMixin`, `AbstractRecipeBookScreenMixin`): the uses key over a slot opens the book on its first tab and keeps, among the collections the tab, search and filter leave, those with a recipe whose `craftingRequirements` take the item; the search field's hint names it. Typing a search or closing the book drops it. Client only: the client knows the displayed recipes' ingredients. `-Ptests=RecipeUses`.
- **Comparing gear** (`GearComparisonTooltip`): with Shift, an armor piece (by its `equippable` slot) or an item with attack damage in the main hand adds the difference of its flat attribute modifiers with the stack in that slot, in the game's own wording; nothing for the very stack worn or an item without modifiers there (elytra). Client only. `-Ptests=GearComparison`.
- **Chain crafting** (`crafting/ChainCrafting`, `AbstractCraftingMenuMixin`): when the recipe book asks for a recipe the inventory cannot make, the server works out the steps on counts (plain shaped and shapeless recipes the player knows, that fit the grid, at most 4 deep), then applies them all at once or not at all. The client sends the placement of a recipe it shows as missing anyway, so nothing changes on its side: the button stays red until then. Ingredients with a crafting remainder are not used for steps.
- **Shulker boxes** (`storage/ShulkerFilling`, `ItemMixin`, `client/storage/ShulkerMouseActions`): the box is a plain `BlockItem`, so `Item.overrideStackedOnOther`, `overrideOtherStackedOnMe` and the bar methods are patched for it, on the model of `BundleItem`. Both sides run the clicks, the client predicting; `ServerSupport.has` keeps vanilla's on a server without the mod. A box with a loot table refuses, not to lose it. The stack picked with the wheel is kept per player on each side (`Select` payload), not on the item: it lasts while hovered. The drags are the bundle's (`AbstractContainerScreenMixin`). What a bundle does when used in the world, throwing its items out, has no equivalent: using a box places it.
- The durability warning only watches enchanted items in hand and in the armor slots, and only as they wear: the client compares each slot with the tick before, so an item already worn when taken in hand stays quiet (switching hotbar slots counts as taking another item). It warns at 5 % of the durability, at least 10 uses, then at 3 uses, without telling how many are left. Client only: it works on any server.

### Small tweaks

- **Sweet berry thorns** (`SweetBerryBushBlockMixin`): no damage with both the legs and feet slots filled. `-Ptests=BedAndThorns`.
- **Players' beds** (`tweaks/PlayerBeds`): a bed is a player's when an online player's respawn point is on it. `AcquirePoiMixin` hides it from villagers looking for a home, `SleepInBedMixin` makes one who already claimed it give it up. `-Ptests=BedAndThorns`.
- **Iron golems and fire** (`IronGolemMixin`): `PathType.FIRE` is impassable for them. Tamed animals too (`TamableAnimalMixin`), as they would follow their owner through it; their teleport already refuses a spot next to lava or fire (only `WALKABLE` counts). `-Ptests=StrayMobs`.
- **No creepers** (`tweaks/NoCreepers`, `SpawnPlacementsMixin`): the `cassonade:spawn_creepers` game rule, on by default, built with Fabric's game rule API; off, `SpawnPlacements.checkSpawnRules` refuses creepers for `NATURAL` and `CHUNK_GENERATION` spawns only. `-Ptests=NoCreepers`.
- **Murky water** (`tweaks/MurkyWater`, `LivingEntityMixin`, `TargetGoalMixin`): when the mob's or its target's eyes are under water, `getVisibilityPercent` brings what the mob notices down to 16 blocks of its follow range, as sneaking or a mob's head does, and `TargetGoal.getFollowDistance` to 30 once it chases, where the player's own view ends (`WaterFogEnvironmentMixin`). Server side. `-Ptests=MurkyWater`.
- **Diving mask** (`tweaks/DivingMask`, `item/CassonadeItems`): a helmet of its own `ArmorMaterial` (a leather cap's protection, durability, enchantability and repair), added to the `enchantable/head_armor`, `equippable` and `durability` tags rather than `head_armor`, which would make it trimmable with no trim textures. Worn by the camera's entity under water, `GameRendererMixin` skips the blur and `WaterFogEnvironmentMixin` ends the fog at 63% of vanilla's (60 blocks). Its snorkel: `canBreatheUnderwater` is true for a player wearing it while the point 2.5 blocks above the eyes is out of the water, below a source's surface (`FluidState.getHeight`), and in a block with no collision (`LivingEntityMixin`); air is counted on the server. A player who stops breathing through it while still under water gets 5 seconds of Water Breathing, without particles (`DivingMask.tick`, on `END_SERVER_TICK`). Its textures, the item and the worn layer (`equipment/diving_mask.json`), are drawn by [tools/diving_mask_textures.py](tools/diving_mask_textures.py). `-Ptests=DivingMask`.
- **Bees and the sea** (`BeeWanderGoalMixin`, `tweaks/BeeWandering`): the wander goal's destination is replaced when it lies on open water in an ocean biome, unless the bee is homing from over 24 blocks away from its hive. `-Ptests=StrayMobs`.

A vertex blends the four blocks touching it on the face's outer side, weighted by their light; the light's own faces stay as they are. Its color is left alone: the hue goes in its alpha, always whole on terrain otherwise (5 bits of hue, 3 of saturation, 255 for none), and `shaders/core/terrain.vsh` decodes it and tints the vertex, at 0.65, as much as the lightmap's block light outshines its sky light right now: the sun washes it out by day and it comes back at night, with no mesh built again. Light carried by entities counts too: each `DynamicLights` source keeps the color of the item it comes from (`ColoredLight.color(ItemStack)`: the sculk torch teal, a lava bucket as lava, fire white), and where it outshines the world's light at a block, that block takes its color at its level; a section is tinted when a colored carried light reaches it (`DynamicLights.coloredNear`), and the sections a light leaves or reaches are rebuilt as before. The mod's own blocks follow their names, the waystone's crystal pink. Hues, light reads and vertices are cached per section. The world's light is untouched, and a change of color at the same level only shows once the sections around are rebuilt. About a quarter more time to mesh a section in the Nether, where lava is everywhere; off with Sodium, which meshes terrain itself. `-Ptests=ColoredLight` takes screenshots of six bays, each with its light, then of a waystone seen with a sculk torch in hand, and outdoors of soul lanterns and glow lichen by day and by night.
- **Sculk torch** (`light/SpawnSpots`): twice a second, the client looks 12 blocks around and 8 up and down for spots where a zombie could spawn (`isValidSpawn` on the block below, `NaturalSpawner.isValidEmptySpawnBlock` for the two above) with no more block light than the dimension allows; a sky light above 7 makes it a night-only spot. Each spot gets the creeper's face, 8 by 8, as flat translucent gizmo squares on its ground, dark for any time, light for night only, redrawn every tick. Its texture is drawn by `tools/gear_item_textures.py`: the torch's stick topped with the active sculk sensor's tendril, its 16 frames at 2 ticks each, the sensor's resting pace (`sculk_torch.png.mcmeta`, kept beside the packed texture). `-Ptests=SculkTorch`. Client only.
- **Fire and shield on screen**: client only. `ScreenEffectRendererMixin` wraps `submitFire` in a pose lowered by 0.2; `FirstPersonHandsAndItemsRendererMixin` lowers the pose by 0.2 where `submitArmWithItem` finds the item raised in a block is a shield. `-Ptests=ScreenOverlays` takes a screenshot of each.
- **Poison** (`combat/Poison`): `LivingEntityMixin` halves its duration as `addEffect` adds it, from any source (commands included), and `PotionContentsMixin` the duration in potion and arrow tooltips, only on a server with the mod; `PoisonMobEffectMixin` hurts every 50 ticks instead of 25 (still halved per level). `-Ptests=Poison`.
- **Netherite** (`combat/Netherite`): the sword's default `ATTRIBUTE_MODIFIERS` (Fabric's `DefaultItemComponentEvents`) give 10 attack damage instead of 8; on a server without the mod, its tooltip says 10 while the server deals 8. `PlayerMixin.getDestroySpeed` scales the pickaxe's speed on the `cassonade:deepslate` tag by the block's hardness over stone's (1.5), so it breaks them as fast as stone, and at once with Efficiency V and Haste II. `-Ptests=Netherite`.
- **Enchantment levels**: `data/minecraft/enchantment/` overrides the enchantments that topped out at II (to III) or IV (to V), copied from vanilla with only `max_level` changed; their effects and costs are linear, so the new level follows. The client gets them from the server's registries. `-Ptests=EnchantmentLevels`.
- **Cobwebs** (`WebBlockMixin`): `getDestroyProgress` returns 1, so a web breaks in a single tick with anything in hand, and `PlayerMixin.hasCorrectToolForDrops` answers yes for it, so vanilla's loot table gives string (or the cobweb itself with shears or Silk Touch). Without the mod on the server, vanilla: the client would break a web the server keeps. `-Ptests=Cobweb`.
- **Nether portal frames**: `data/minecraft/tags/block/nether_portal_frame.json` adds crying obsidian to the tag `PortalShape` checks. The portals the game builds on arrival stay obsidian. Server side. `-Ptests=PortalFrame`.
- **Farmland**: a fall on farmland no longer turns it to dirt when the one falling is a player, or a mount a player rides (`FarmlandBlockMixin`). Mobs still trample it, under the `mobGriefing` rule. Server side.
- **Furnace experience**: the server sends the player with a furnace open `FurnaceExperience` (the sum of `recipesUsed` times each recipe's experience, in tenths, read through `AbstractFurnaceBlockEntityAccessor` so no orbs are given out), checked every 10 ticks; `AbstractFurnaceScreenMixin` adds it to the small line showing the furnace's times and fuel, nothing on a server without the mod.
- **Furnaces**: the flame and the arrow are vanilla's sprites with their gray background made transparent by [tools/furnace_progress_textures.py](tools/furnace_progress_textures.py), over the window's own unlit flame and empty arrow; the blast furnace and the smoker use the furnace's. The brewing stand's bubbles and arrow ([tools/brewing_progress_textures.py](tools/brewing_progress_textures.py)) are vanilla's too, with the gray background made transparent and the furnace's yellow and orange. In `AbstractFurnaceScreenMixin`, the time left is the items to cook times the cooking time, minus the time spent, from the timers the window syncs; the fuel's count adds the burning fuel's time left, in cooking times, to the waiting fuel's items (FuelTimes). Both, with the held experience, share one panel next to the window (`InfoPanel`). Client only; on a server without the mod, the waiting fuel does not count.
- **Grindstone**: the client adds up the enchantments' worth as `GrindstoneMenu` does (curses aside) and shows the range the game draws from, half of it rounded up to twice that minus one, where the anvil shows its cost (`GrindstoneScreenMixin`). Client only.
- **Sweeping**: a sweep counts the animals the player owns (`OwnableEntity`: wolves, cats, parrots, horses…) as allies, like teammates, and leaves them alone (`PlayerMixin`). Server side.
- **Own animals in melee** (`combat/OwnPets`, `PlayerMixin`): on the server, `Player.attack` on the player's own `OwnableEntity`, not sneaking, picks the next entity along the view within reach, or does nothing; a spear's `stabAttack` skips them. A horse's owner never reaches the client, so the client cannot do this itself. On a server without the mod, melee stays vanilla.
- **Chat mentions**: a chat message from anyone but the player whose text has their name as a word of its own, in any case, rings a note block bell (`ChatMentions`). Fabric's chat event fires just before the message is added to the chat, where `ChatComponentMixin` rebuilds it piece by piece, styles kept, the name in gold. Client only.
- **Armor stands**: `Alt` (the slot lock's key, `client/ArmorStandSwap`) and a right click with an empty main hand sends `SwapArmorPayload`, which swaps the four armor slots with the stand's, each slot on its own: a piece with Curse of Binding stays on (outside Creative), and the stand's `DisabledSlots` are read as `ArmorStand.swapItem` does (`ArmorStandMixin`). On a server without the mod, the click stays vanilla. Sneaking, the same click goes through `tweaks/ArmorStandPoses`, whose current pose is read from the stand itself.
- **Woodcutter** (`woodcutter/`): a `StonecutterBlock` and `StonecutterMenu` subclass with their own block, item and menu type (the stonecutter's screen is reused with a wood-toned background, recipe buttons and scroller from `tools/container_panels.py`). Its recipes are `minecraft:stonecutting` recipes with a plank as input in `data/cassonade/recipe/woodcutter`, written by `tools/woodcutter_recipes.py`; `StonecutterMenuMixin` (both sides) offers a plank only to the woodcutter and everything else only to the stonecutter. It also remembers, on the server, the piece picked while the menu is open and selects it again for the next stack, or the piece with the same last word in its name for another material; the client resets its selection by itself, so the remote data slot is cleared to send the index again. `LoomMenuMixin` does the same with the banner pattern. The block textures are the stonecutter's recoloured by `tools/woodcutter_textures.py`.
- **Dyed blocks**: `CauldronInteractionsMixin` registers, through `CauldronDispatcherAccessor`, a water-cauldron interaction for every dyed wool, carpet, bed, terracotta, glass and glass pane. It washes the whole held stack for one level of water. Concrete powder hardens and filled maps go blank the same way, the map as a new stack so its id is dropped.
- **Paintings** (`client/PaintingChoice`, `tweaks/ChoosePaintingPayload`): placing stays vanilla. `MouseHandlerMixin` sends the wheel when sneaking and aiming at a painting with one in either hand, or with an empty main hand at the spot of the last placed (remembered on the client). The server walks the `placeable` tag from the current variant, largest first, and keeps the next that `survives()`. On a server without the mod, the wheel stays vanilla.
- **Safe bridging** (`client/SafeBridging`, `MultiPlayerGameModeMixin`): sneaking, a click on the far side of the top of the block underfoot is sent as a click on its far face, low on it so slabs stay at the bridge's level. Blocks without collision stay where aimed. `FacingPreview` asks the same. The server checks only the reach, so it works on any server.
- **Name tags** (`NameTagItemMixin`, `client/NameTagTooltip`): a tag without a custom name toggles the vanilla `Silent` flag, which needs no other change as the game skips the sounds of a silent entity. `Mob.interact` asks name tags before a mob's own use, so it works on villagers.
- **Villager's workstation** (`trader/WorkstationPayload`, `VillagerMixin`, `client/trader/WorkstationButton`): the job site memory is sent when trading starts; a click turns the player towards it (`lookAt`, sent as any other move) and shows a client-only ping (`Pings.show`).
- **Snow** (`tweaks/SnowShovel`): a `UseBlockCallback`, as block transformers cannot give a snowball; one layer, one snowball, one use of the shovel. Server side.
- **Mouse button 4** (`client/MouseBack`): calls the screen's `onClose` where `Esc` would, unless a key mapping uses that button or the controls screen is waiting for one. Client only.
- **Ender chests**: the loot table `data/minecraft/loot_table/blocks/ender_chest.json` replaces vanilla's; the block already needs a pickaxe to drop anything.
- **Armor stand arms**: a stand placed from the item gets its arms (`ArmorStandItemMixin`), as in Bedrock Edition; shears on a stand with arms take them off, drop what its hands held and wear by one use, and two sticks on a stand without arms put them back (`ArmorStandMixin`). Stands summoned or loaded keep their own `ShowArms`. Server side.

### Combat

Everything shows only to a player wearing a sculk compass. Only the server knows what a mob targets: it sends that player, every 2 ticks when it changes, the list of mobs chasing them within 64 blocks (a ghast's reach), from scratch each time the compass is worn again. The same list puts the hunters on the minimap, as red dots kept on its edge when out of range; a mob too far for the client to know where it is (past its tracking range) is left out. On a server without the mod, only the bars of hurt mobs show, with no "!", eye or dots. Health bars show up to 32 blocks away, as far as the list goes for the mobs chasing the player, only for mobs in sight, and stay 5 seconds after the last hit. The sprites are generated by `tools/combat_textures.py`.

**Boss bars.** [BossBars](src/client/java/com/cassonade/client/BossBars.java) draws them in place of vanilla's (`BossHealthOverlayMixin`), which keeps the events, the music, the darkening and the fog. The server only sends how full a bar is: the damage shown is the drop times the maximum health of the nearest mob named like the bar, and is left out when none is (raids, `/bossbar`). While a boss bar is shown, the direction bar is hidden (`MarkersInWorld`), and the mob it is named after gets no health bar from `CombatHud`. The sprites are generated by `tools/boss_bar_textures.py`; `-Ptests=BossBar` takes screenshots.

The other players show on the minimap as far as the client knows of them (its entity tracking range), spectators and invisible players left out, as vanilla's blue map marker turned the way they look, with their name. Client only: it works on any server.

### Spyglasses

- The naturalist's spyglass zooms like the vanilla one, scope and slower aim included: `PlayerScopingMixin` makes `isScoping()` true while it is used, as the game only knows its own spyglass. The server never asks, so only what the client draws changes.
- Through either spyglass, the scroll wheel picks one of three zooms, the game's (a field of view scaled by 0.1) between 0.05 and 0.2 (`ScopeZoom`, `AbstractClientPlayerMixin`; `CameraMixin` lets the camera go below 0.1), instead of the item in hand (`MouseHandlerMixin`). Back to the game's each time the spyglass is raised.
- The scope (`textures/misc/spyglass_scope.png`, over the game's) is a round lens at the end of a dark tube, in the colors of the game's frame and glass, drawn by [tools/scope_texture.py](tools/scope_texture.py).
- The panel shows while looking through the naturalist's spyglass, for what is picked along the view up to 128 blocks, about as far as the client keeps track of animals, each mob widened by 0.3 blocks to be easier to aim at from afar. The look goes through the plants with no collision that it has nothing to read about (grass, ferns, flowers), so they hide nothing behind them; crops and beehives stop it. It reads what the client knows: a horse's attributes (speed in blocks per second is the attribute × 42.16, the jump height a fit of the game's physics), each drawn as a bar from the worst value a horse is born with to the best (speed 0.1125 to 0.3375, jump strength 0.4 to 1, 15 to 30 health; a llama's strength 1 to 5), a villager's level, a crop's `age`, and a beehive's honey and occupant count. Beehives send their occupant data to clients when the count changes (`BeehiveSyncMixin`); a vanilla client ignores it. A mob's age and a villager's trades are only on the server: the client asks every second about the mob looked at (`GlanceRequestPayload`, ignored past 128 blocks or without the naturalist's spyglass in hand) and counts the age down between answers. A villager never traded with has no trades yet, and they are not generated just to be counted.
- A chest's, barrel's or Shulker box's name, given at the anvil, shows in the same panel, through the spyglass or at arm's length; a double chest takes it from either half. Vanilla sends the client nothing of these block entities: with the mod, the server sends their name alone, never their contents (`ContainerNameSyncMixin`). On a server without the mod, it does not show.
- A playing jukebox shows its song's name in the same panel, at arm's length. The client never sees the disc: it learns the song from the level event that starts it, which `LevelEventHandlerMixin` records by position, so this works on a vanilla server too.
- With a honeycomb or an axe in hand, a copper block looked at at arm's length shows whether it is waxed: the game's own pairs of waxed and unwaxed blocks (`HoneycombItem.WAXABLES`). Client only.
- With redstone dust in hand, a wire looked at at arm's length shows its `power` state, and any other block the strongest signal its neighbors give it (`Level.getBestNeighborSignal`), worked out by the client from the block states it has. Client only.
- A note block's note is read from its `note` state (0 is F♯3, each step a semitone) in the same panel, through the spyglass or, without it, from the block under the crosshair at arm's length.

### Wandering traders

- While a wandering trader's `MerchantMenu` is open, the server sends its despawn delay every second (`TraderTimePayload`, via `MerchantMenuAccessor`). The merchant screen shows it in the info icon's tooltip, as is: vanilla pauses the delay while the trader is trading. On a server without the mod, the vanilla screen is unchanged.

### Quest journal and advancements

- The game only sends the player the advancements close to those already earned. With the mod, the server sends them all (in singleplayer, the integrated server has the mod). On a server without the mod, the list is limited to what it sends.
- The mod's own advancements (backpack, organized backpack, compass, world map, marker, clock, barometer, sculk compass) are granted by the server checking the player's equipment and markers every second, even for equipment worn before they were added. They make up the "Explorer's Gear" chapter, apart from the sculk compass's and the organized backpack's, in the ruins chapter with the deep dark. The barometer's needs the clock's, the sculk compass's the compass's.
- The game's 126 advancements and the mod's 11 are spread across the chapters in [chapters.json](src/main/resources/assets/cassonade/quests/chapters.json). Chapter titles, introductions and quest hints are in the language files (`quest.cassonade.*`); a quest without a hint shows the advancement's description.
- The choice to follow the journal and the followed quest are saved per world, in `cassonade/quests.properties`; the tracker display in `config/cassonade.properties`.
- `QuestOffer` asks for that choice in the HUD, in the tracker's place. While it shows, `OPEN_JOURNAL` answers yes and `QUEST_TRACKER` no instead of their usual role; its buttons can be clicked from the screens that free the cursor. Its 20 seconds only run with no screen open, and ignoring it saves nothing, so it comes back on the next join. In the tests, `QuestLogMixin` declines it on joining any world; only `QuestOffer` sets `JournalOffer.shown`, and `JournalOffer.follow` takes up the journal.
- The textures (frames, medallions, rays, button icons, journal cover) are drawn by [tools/quest_textures.py](tools/quest_textures.py).

### Waystones

`waystone/`: `WaystoneData` (a `SavedData` on the overworld) lists every waystone, written in `onPlace` and removed in `affectNeighborsAfterRemoval` so commands and explosions count; pistons cannot move it. A player only sees or travels to those in the entry's `discoveredBy`: the one who placed it (`setPlacedBy`) and whoever `Waystones.discover`, each second, finds within 32 blocks. Using one sends `WaystoneListPayload`, and `client/waystone/WaystoneScreen` answers with `WaystoneTravelPayload`, checked again by the server: the player in reach of the source, the target still a waystone, with a free spot on the ground among the eight around it. The block has two halves held together like a door's (`HALF`), only the lower one listed and dropping the item; the item model stacks both. `WaystoneRenamePayload` carries the name typed in that screen, which the server accepts from the entry's `owner` only, or anyone if it has none (placed by a command); a blank one means the default, drawn on the client from the dimension and coordinates. The crystal turns, so it is no part of the block's model: a block entity on the top half, without data, has it drawn by `client/waystone/WaystoneCrystalRenderer`; the item's model holds it still. It moves as an active conduit does: a cube on a slanted axis, bobbing, with portal particles drawn in (`WaystoneBlock.animateTick`) letters as to an enchanting table, and dark purple motes tracing a double spiral around it (a client ticker, `WaystoneBlock.spark`). The world map and the minimap ask for the list (`WaystoneMapRequestPayload`, answered only with a world map or a compass worn, with the same waystones as the list), the first on opening, the second every 5 seconds to see those discovered, renamed or broken since; the client keeps it in `client/map/WaystoneMarkers`, and they and `MarkersInWorld` draw those of their dimension, without a click of their own; their icon comes from `tools/dimension_icons.py`. Its textures come from `tools/waystone_textures.py`: the End crystal's core, its symbols replaced by the letters of PORTAL in the enchanting table's alphabet; the stone's are hand edits in `src/textures/world.png`.

### Filtered hopper

The filter is a real item, given back when the hopper is broken, and compares the item only, not its components. A bundle or shulker box with items in it lists the accepted items (only one level deep: the containers it holds are not opened); an empty one filters itself. The hopper's speed, redstone locking and comparator output (which ignores the filter) stay vanilla. Its textures are derived from the hopper's by [tools/filtered_hopper_textures.py](tools/filtered_hopper_textures.py).

## Textures and interface

The interface follows one art direction: plain panels of sepia wood with plum shadows and golden edges, near-black slots, tan leather for the backpack and books, cream paper for pages. Hover is a cream outline (ribbon red on paper), selection a green frame. Vanilla icons keep their shape.

**The interface atlas.** All interface textures (HUD, windows, widgets, recipe book, backpack…) live in a single image, [src/textures/gui.png](src/textures/gui.png), arranged in titled sections. Edit it in a drawing program and relaunch the game: the build cuts it back into files according to [src/textures/gui.json](src/textures/gui.json). Each texture is cropped to its visible pixels (an empty texture keeps its whole area) and surrounded by a bright pink frame with its name above: paint inside the frame. Frames, names and gaps are ignored.

- To add a texture, drop it at its place under `src/main/resources/assets`, then run `python3 tools/gui_atlas.py`. Without a new texture, the same command rearranges the image.
- **The other textures** (blocks, items, the view through a spyglass, the mod's icon) live the same way in [src/textures/world.png](src/textures/world.png), with [src/textures/world.json](src/textures/world.json): `python3 tools/world_atlas.py` packs what it finds under `src/main/resources/assets`. A script drawing one of them writes its PNG there, to be packed after, which replaces hand edits of that texture.

**Info icons.** Some container screens show information in a tooltip, revealed by hovering a discreet "!" icon right of the window's title, where the sort buttons sit: [InfoPanel](src/client/java/com/cassonade/client/InfoPanel.java). The icon is drawn like the sort and search buttons (`storage_info` sprites, engraved dark, white when hovered; `tools/gui_textures.py`); the tooltip is a real one, a row per line, each pairing a gold subject with a cream value, and shows nothing (no icon) when there is no row. A new screen needing container information should use it rather than draw its own text. The anvil is the exception: its cost stays where vanilla draws it, on a sunk field in the mod's style (`InfoPanel.sunk`). Every screen that uses the icon:

| Screen | Line shown | Data |
|---|---|---|
| Grindstone ([GrindstoneScreenMixin](src/client/java/com/cassonade/client/mixin/GrindstoneScreenMixin.java)) | Experience given back (a range) | Computed on the client from the items |
| Furnace, blast furnace, smoker ([AbstractFurnaceScreenMixin](src/client/java/com/cassonade/client/mixin/AbstractFurnaceScreenMixin.java)) | Cooking time, fuel remaining and stored experience, each on its own line | Menu data; fuel in waiting needs `FuelTooltip` and experience `FurnaceExperienceTooltip`, both fed by the mod's server (without it, only the burning fuel counts and no experience is shown) |
| Brewing stand ([BrewingStandScreenMixin](src/client/java/com/cassonade/client/mixin/BrewingStandScreenMixin.java)) | Time left and number of brews the fuel can still make, on separate lines | Menu data |
| Wandering trader ([WanderingTraderMerchantScreenMixin](src/client/java/com/cassonade/client/mixin/WanderingTraderMerchantScreenMixin.java)) | Time before the trader leaves | `TraderTimePayload` from the server; nothing is shown without the mod |

Update this table when a screen is added or changed. The anvil ([AnvilScreenMixin](src/client/java/com/cassonade/client/mixin/AnvilScreenMixin.java)) only lifts the "Too Expensive!" cap and restyles vanilla's cost line. The other tooltips of the mod (food, maps, storage contents, enchantments) are real item tooltips, and the crosshair's [GlancePanel](src/client/java/com/cassonade/client/spyglass/GlancePanel.java) is a HUD panel, not part of this list.

**Never run `tools/build_gui.py`** unless you mean to start over: it redraws every texture from the scripts and replaces `src/textures/gui.png`, wiping every hand edit made in the image. The starting colors are in [tools/gui_theme.py](tools/gui_theme.py), the shapes in [tools/gui_style.py](tools/gui_style.py) (HUD, windows, widgets), [tools/gui_textures.py](tools/gui_textures.py) (backpack, bookmark), [tools/recipe_book_textures.py](tools/recipe_book_textures.py) and [tools/enchanting_book_textures.py](tools/enchanting_book_textures.py) (isometric enchanting book). `tools/panel_textures.py` draws the HUD panels, `tools/search_field_texture.py` the storage search field, `tools/cartography_textures.py` the cartography table's map sheets.

**Other textures** are drawn by dependency-free Python scripts (`tools/*_textures.py`, with `tools/pngio.py`), colors from `tools/gui_theme.py`. The mod's icon, a lump of cassonade on a wooden panel, is drawn by [tools/icon_texture.py](tools/icon_texture.py), which also writes the website's copy. The share image (`promo/site/assets/og.jpg`, also the repository's social preview) is [tools/og-image.html](tools/og-image.html) rendered by Chrome, as its comment explains.

**Title screen.** [TitleScreenMixin](src/client/java/com/cassonade/client/mixin/TitleScreenMixin.java) keeps vanilla's screen, its panorama and its widgets (demo, disabled multiplayer, other mods' buttons) and only moves them: the logo, at half its size and centered on the buttons, in a column on the left, centered in height, over a shade of the loading screens' color fading out to the right. The version and the credits, in `SmallText` and faded (through [SmallTextButton](src/client/java/com/cassonade/client/SmallTextButton.java) for the credits, which turn fully opaque when pointed at), stay a margin away from the edges. The Realms icons follow through the size passed to their `init`. `-Ptests=TitleScreen` takes screenshots, in English at 1920×1080 and in French at the smallest GUI.

**World selection.** [WorldSelectionScreen](src/client/java/com/cassonade/client/WorldSelectionScreen.java) subclasses `SelectWorldScreen`, which `GuiMixin` swaps for it whenever vanilla's exact class opens. Loading the worlds, searching, playing, editing, re-creating and deleting stay vanilla's `WorldSelectionList`: the screen only lays it out in a `FramedPanel` over the loading screens' background and draws the panel of the world selected. The list is restyled for this screen only (`WorldSelectionScreen.styles`): `AbstractSelectionListMixin` drops its background, separators and selection outline and puts the rows at the panel's edge with the scrollbar inside, `WorldSelectionListMixin` widens the rows, `WorldListEntryMixin` draws them, `AbstractScrollAreaMixin` draws the scrollbar as a sunk groove with a wooden handle; the Realms upload list stays vanilla. The time played comes from the player's statistics in the save (`players/stats`), read once per world while the screen is open. `-Ptests=WorldSelection` creates three worlds and takes screenshots, in English at 1920×1080 and in French at the smallest GUI (426×240).

**Server selection.** [ServerSelectionScreen](src/client/java/com/cassonade/client/ServerSelectionScreen.java) subclasses `JoinMultiplayerScreen`, which `GuiMixin` swaps for it whenever vanilla's exact class opens. Vanilla's `init` makes the widgets and starts the local network's search; the screen only moves them into the same panels as the world selection, without rebuilding them on a resize, which would start another search. `OnlineServerEntryMixin` lets vanilla's ping run and then draws the row, `NetworkServerEntryMixin` and `LanHeaderMixin` draw the others, and `ServerSelectionListMixin` widens the rows; the shared restyling goes through `WorldSelectionScreen.styles`. A server whose address cannot be resolved stays `PINGING` in vanilla: a description already set marks it as out of reach. `-Ptests=ServerSelection` lists three servers, one made to look online, and a local world, and takes screenshots, in English at 1920×1080 and in French at the smallest GUI (426×240).

**Menus and dialogs.** `ScreenMixin` gives every menu shown without a world the loading screens' background; the title screen draws its own panorama. `GenericMessageScreenMixin` does the same for vanilla's other messages, which draw the panorama themselves, with the message in a panel. Small dialogs keep vanilla's widgets and logic in a `FramedPanel` ([DialogPanel](src/client/java/com/cassonade/client/DialogPanel.java)): `ConfirmScreenMixin` and `DisconnectedScreenMixin` around vanilla's layouts, `AlertScreenMixin`, `BackupConfirmScreenMixin`, `DirectJoinServerScreenMixin` and `ManageServerScreenMixin` moving their fixed positions to the middle of the screen. [PauseScreenMixin](src/client/java/com/cassonade/client/mixin/PauseScreenMixin.java) only colors the title of vanilla's centered menu. [DeathScreenMixin](src/client/java/com/cassonade/client/mixin/DeathScreenMixin.java) keeps vanilla's red veil with everything in a panel, under the skull of `tools/loading_textures.py`, which a very small window leaves out. `MenuTabButtonMixin` removes the background vanilla paints inside the selected tab. `SocialInteractionsScreenMixin` and `PlayerEntryMixin` swap that screen's frame and rows. `-Ptests=MenuScreens` takes screenshots, in English at 1920×1080 and in French at the smallest GUI.

## Recipes

The rebalanced recipes are generated from the vanilla jar by [tools/rebalance_recipes.py](tools/rebalance_recipes.py). Only the output amount changes: shapes, recipe book groups and unlocks stay vanilla. The same script writes the stairs and slabs → blocks and wool → string recipes in `data/cassonade/recipe/uncraft`. To adjust a number, edit the `RULES` table and run the script again:

```sh
python3 tools/rebalance_recipes.py ~/Library/Application\ Support/minecraft/versions/26.3/26.3.jar
```

## Translations

Every displayed text goes through the language files in `src/main/resources/assets/cassonade/lang/`. Keep every locale in sync: `en_us.json`, `fr_fr.json`, `es_es.json`, `pt_br.json`, `de_de.json`, `zh_cn.json`, `ru_ru.json` and `ja_jp.json` should cover the same keys. New languages are welcome: copy `en_us.json` under the game's locale code, translate the values, and preserve formatting placeholders such as `%s` and `%1$s`.

## Documentation

A change players can see updates, in the same commit:

- the [README](README.md) (the feature's section, and the tables if needed);
- the website, if the feature is shown there: [promo/site/_data/en.yml](promo/site/_data/en.yml) and [promo/site/_data/fr.yml](promo/site/_data/fr.yml), always both. Each feature has its section on the home page and a page of its own (`promo/site/features/`, `promo/site/fr/fonctionnalites/`), whose texts are the feature's `detail` in the same files; the page files only hold its title and description for search engines. The icons of their crafting grids are copied from the game's textures by [tools/site_recipe_icons.py](tools/site_recipe_icons.py); the blocks among them (lightning rod, sculk sensor, woodcutter), which have no flat texture, are drawn by the game itself, with `./gradlew runClientGameTest -PsiteIcons` (`SiteIconsClientGameTest`), only when one of them changes: the sculk sensor's and the woodcutter's textures are animated, so each run catches another frame. A recipe that fits the inventory's crafting grid shows in a 2×2 grid, the others in the crafting table's 3×3.

The [CHANGELOG](CHANGELOG.md) is never edited by hand.

## Commits

Messages follow [Conventional Commits](https://www.conventionalcommits.org/), in English: `feat(<feature>): <what the player gains>`, `fix(<feature>): <what is fixed>`. The scope is the feature: `backpack`, `compass`, `world-map`, `clock`, `inventory`, `farming`, `elytra`, `hopper`, `quests`, `combat`, `spyglass`, `recipes`, `tweaks`, `interface`. Website changes are `docs(site): …`.

The message describes the result for the player, not the implementation: `feat(hopper): give every hopper a filter slot`. [git-cliff](https://git-cliff.org) writes the CHANGELOG from them (settings in [cliff.toml](cliff.toml)); only `feat`, `fix` and `perf` appear in it. One line per feature or fix: a later commit that only carries on one not released yet (a feature tuned, extended or fixed before release) ends with a `Changelog: skip` trailer, and the first commit's message is reworded, before pushing, to describe the feature as it ships.

## Releasing

The version lives in `gradle.properties` and is only changed by the release workflow, started by hand from GitHub: Actions tab → Release → Run workflow, choosing the version type:

| Choice | Effect |
|---|---|
| `alpha`, `beta` | next pre-release: 0.1.0-alpha.1 → 0.1.0-alpha.2, then → 0.1.0-beta.1 |
| `release` | final version of a pre-release: 0.1.0-beta.2 → 0.1.0 |
| `patch`, `minor`, `major` | 0.1.0 → 0.1.1, 0.2.0, 1.0.0 |

The workflow ([release.yml](.github/workflows/release.yml)) updates the version, adds the CHANGELOG entry, builds the mod, commits both files, tags `v<version>` and publishes the jars in a GitHub release, with the CHANGELOG entry as notes; a pre-release is marked as such. The jar is then uploaded to Modrinth and CurseForge, each once its project id is set as a repository variable (`MODRINTH_ID`, `CURSEFORGE_ID`) with its token as a secret (`MODRINTH_TOKEN`, `CURSEFORGE_TOKEN`). The version is computed in [tools/next-version.sh](tools/next-version.sh). Never tag by hand. To preview the entry that will be added: `git cliff --unreleased` (install git-cliff with `brew install git-cliff`).

The Modrinth page follows `promo/store/`: on each push changing it, [store.yml](.github/workflows/store.yml) sends `promo/store/summary.txt`, `promo/store/description.md` and the images of `promo/store/screenshots/` (`tools/modrinth_sync.py`), which replace the gallery, in the order and with the titles and captions of `promo/store/gallery.json`, most important first; `MODRINTH_TOKEN` needs the `PROJECT_WRITE` scope. Started by hand with `dry_run`, it only lists what would change. New images are added before the old ones go; when the gallery is full, an old one is removed to make room. CurseForge has no API for a project's page, so nothing sends `promo/store/` there on a push: after changing it, run [tools/curseforge_sync.py](tools/curseforge_sync.py) by hand, from a Mac. It works from the authors' site in a Chrome of its own (profile in `~/Library/Application Support/cassonade-store-chrome`, debugging port 9334), which keeps the sign-in from one time to the next:

```sh
python3 -m venv ~/.cache/cassonade-store && ~/.cache/cassonade-store/bin/pip install websocket-client   # once
PY=~/.cache/cassonade-store/bin/python
$PY tools/curseforge_sync.py open      # sign in by hand if asked: the tool never types a password
$PY tools/curseforge_sync.py text      # description and summary, if they changed
$PY tools/curseforge_sync.py gallery   # every image, a few minutes
$PY tools/curseforge_sync.py check     # what the gallery holds against promo/store/gallery.json
$PY tools/curseforge_sync.py close     # while it runs, any local program can drive the session
```

`gallery` always replaces every image, as the site ignores bytes it already holds: through the API the site's own page uses (`/_api/image-attachments`, from that page, which holds the session), it removes them all, sends the new ones by batches of 20, the site's limit, then writes their texts, the first four as featured and the order. If it stops, run it again. The authors' site answers from copies of the list that can be minutes old, showing images long gone: `check` reads the public page instead. The API is undocumented: look at the site's scripts if it changes.

Every push to `main` and every pull request also build the mod ([build.yml](.github/workflows/build.yml)); the jar can be downloaded from the Actions tab.

## Website

The mod's website is in [promo/site/](promo/site/), a Jekyll site published on GitHub Pages on every push to `main` that changes it ([pages.yml](.github/workflows/pages.yml)). One page in English (`/`) and French (`/fr/`): the text is in [promo/site/_data/en.yml](promo/site/_data/en.yml) and [promo/site/_data/fr.yml](promo/site/_data/fr.yml), the layout in [promo/site/_layouts/home.html](promo/site/_layouts/home.html), shared facts and store links in [promo/site/_data/mod.yml](promo/site/_data/mod.yml). The home's comparison table is split by theme (`compare.groups`, one accordion each), and a feature made of many small things groups its points in chapters (`detail.sections` instead of `detail.points`); a chapter can end on a table (`table`: an `intro`, a `head` and `rows`, the first cell of each row naming it), which turns into labeled cards on a phone, like the enchantments' levels on the small tweaks page. Screenshots go in [promo/site/assets/screenshots/](promo/site/assets/screenshots/).

The home page is read as one Minecraft day. Each section carries its hour (`data-time` in `home.html`, shown above its title in place of a chapter number), and the script at the end of `home.html` turns the reading position into a time between those hours: it drives the sky fixed behind the page (`.sky`: a warm brown by day through `--daylight`, a gold glow on the horizon at sunrise and sunset through `--glow`, stars at night) and the clock drawn like the mod's HUD in the bottom-left corner (`.hud-clock`, on screens 1780 pixels wide and more, where it stays clear of the showcases' tabs). A new section needs its own `data-time`, later than the one before. The sections are transparent over that sky; the hero is the uncropped aurora capture (`ambience-aurora`), fading into it at its foot. The site takes the colors of the mod's own interface ([gui_theme.py](tools/gui_theme.py)), the same as the icon, the YouTube banner and the thumbnail: a sepia wood (`--wood*`, `--leather`, `--outline` for panels, frames and buttons; `--card` and `--bg*`, the dark brown of the slots, for cards and backgrounds), plum only in the darkest shadows (`--night`), gold (`--gold*`, also `--aurora`) for accents and hours, and cream for text. Do not add another hue. The living world comes first, right under the hero (`living_world`: the day as one panorama, a band per moment from dawn to night, the band under the pointer opening wide with its caption and its `sounds`, written as the game's own subtitles; under it, `catalogue` lists in short everything the living world adds, by theme), so its `ambience` feature is left out of the groups; its page and carousel are unchanged. The features are grouped under `features.groups` in each data file (a title and the ids of its features, in order): a new feature must be added to a group to appear. Each group is a showcase, its features listed as tabs on the left and the selected one on the right, at its own height: its screenshots with its title, item, keys and a link to its page beside them on a wide screen (1300 pixels and more), its points underneath on two columns. The fixes (`compare.groups`) show one theme at a time the same way. On a screen 960 pixels wide or less, or without JavaScript, the tabs are hidden: the features follow one another with their points folded under « Read more », and the themes of fixes become an accordion. The keys are grouped by the item that unlocks them (the `needs` of each row in `controls.rows`, drawn with its icon from `controls.icons`; rows needing nothing go under `controls.always`), and the fair recipes are a list on two columns, each line read from its `vanilla` and `mod` strings, split on the arrow (what goes in, the vanilla count struck out, Cassonade's). The top bar ([topbar.html](promo/site/_includes/topbar.html)) is shared by every page: the section links, a switch showing both languages with the current one lit, and a single Download button leading to the install section, where every download is; at 960 pixels or less, the links fold into a menu. A feature's page ([feature.html](promo/site/_layouts/feature.html)) sits under the same sky, held at late afternoon: its title with the item and keys beside it, its screenshots large, then its points (each chapter of `detail.sections` in a panel of its own) beside the recipe and requirements, which stay in view. It ends on the features before and after it and a thumbnail of every other one, in the home page's order (the living world, then `features.groups`), using each feature's `-640.avif` screenshot. Pages use three widths: the text column (`.wrap`, `--normal`, 1140 pixels), and inside it blocks that break out on both sides, `.wide` (`--wide`, 1440 pixels: the showcases, the fixes, the living world's list, a feature's screenshots and links) and `.full` (the whole screen: the panorama of the day). Titles and text stay in the text column; the panorama's edge bands keep their texts in line with it. Screenshot AVIF files need even dimensions: sips writes files Chrome cannot decode otherwise.

The site's code follows the principles of [the author's portfolio](https://corentin-gautier.github.io/): HTML and CSS before JavaScript and browser features before a library (no framework, no dependency; JavaScript only where nothing native does it, and the page works without it), nothing loaded that the page does not use (images lazy, the video a link rather than an embed), screenshots in AVIF at the size they are shown (`sizes` on each `shot.html`), the system's font for the text (Monocraft, for titles, is the only font downloaded; the share image and banner scripts keep Nunito Sans in `tools/fonts`), no tracker or third-party script, and pages usable with a keyboard and a screen reader (a link to the content first, tabs driven by the arrows, nothing moving with reduced motion).

To preview it locally, with Ruby and the `jekyll`, `jekyll-seo-tag`, `jekyll-sitemap`, `jekyll-github-metadata` and `webrick` gems installed: `jekyll serve` in `promo/site/`.
